# Emotion audit: GraphForge for VS Code — full-product (blind-spot completion pass)

Audited against `origin/main` @ `441f6e7` (same commit as the prior comparative audit — worktree at `graphforge-vscode-audit`, refreshed via `git fetch && git reset --hard origin/main` immediately before this pass). This is a **standalone** audit, not a comparison — no external product this time.

**Read first, do not re-report:** [`graphforge-vs-kilocode-audit.md`](./graphforge-vs-kilocode-audit.md), completed minutes earlier, covers Get Started (Welcome + checklist), status bar, setup recovery, Run Query, Result Graph, Ontology tree/viewer, and the published install doc, and is already being filed as GitHub issues (P0 Welcome-card ARIA, tooltip diagnostic leak, raw Run Query error toast, dangling checklist action, stale install doc, query progress, Copy Environment Report). Findings below reference that audit as **"known"** in one line where relevant and otherwise cover *only* the blind spots it explicitly named.

## Feeling contract

Restated from `docs/DESIGN.md` (re-verified this pass, unchanged): GraphForge should feel like a **workbench, not a database admin console**. Palette-first (analyst verbs are peers, not Cypher-plus-afterthoughts); epistemic legibility (belief/ontology status always named); progressive, not shaming; fail-closed, never a dead end. Never-feel: raw stack traces in a panel/toast, infrastructure-jargon walls, admin-console coldness. `docs/PRODUCT.md` adds the persona split this pass leans on: **analysts/researchers are the primary audience; integrators/maintainers extending `@graphforge/node` are explicitly secondary.**

## Scope & coverage

**Surfaces audited this pass (read actual source, not summaries):**
1. Knowledge view — tree (`src/views/knowledgeTree.ts`), all 7 commands (`src/commands/knowledgeCommands.ts`): List/Create/Show/Show-on-Graph Assertion, Attach Evidence, Assess Confidence, Record Assertion Status
2. The six analyst-verb QuickPick chains — `src/commands/analystVerbs.ts` (Rank/Cluster/Paths/Analyze/Similar + `*Advanced`) and `src/commands/find.ts` (Find, deliberately a separate module)
3. Power features — checkpoints (`src/commands/checkpoints.ts`, 6 commands incl. destructive revert), embedding spaces (`src/commands/embeddingSpaces.ts`, 6 commands), index management (`src/commands/indexManagement.ts`, 6 commands), power/engineer commands (`src/commands/power.ts`, 5 commands: write mode, enable capability, export descriptor, list algorithm runs, publish composite transaction)
4. Command palette surface as a whole — all 59 entries in `package.json#contributes.commands`, cross-referenced against `src/test/extension.test.ts`'s command-ID contract list
5. Python vs Node runtime parity — `src/session/pythonBridge.ts`, `pythonLoader.ts`, `pythonProbe.ts`, `pythonInstallCommand.ts`, `runtimeSelection.ts`, `runtime.ts`, `commands/setupPython.ts`, and the `EngineBackend` interface in `session/types.ts`
6. Agent persona / interop contract — re-read `docs/experience/agent-interop.md`'s command table against every command handler's actual return type, plus `src/test/extension.test.ts`'s "safe commands" suite

**Not yet covered (still blind spots after this pass):**
- Live rendering of any of the above in an Extension Development Host — everything here is traced from source, same limitation the prior audit named.
- The Node native-binding side of checkpoints/embedding spaces/indexing (`@graphforge/node`'s actual runtime behavior) — this audit only traces the VS Code extension's command layer and `GraphForgeSession`'s dispatch logic, not the engine binary itself.
- `python/graphforge_host.py`'s own error-message quality (what Python exceptions look like *inside* the bridge protocol) beyond what's visible from the TypeScript-side `PythonBridgeError` wrapping.
- Composite transaction and invocation-descriptor *content* validation (whether a malformed JSON payload against the engine produces a good error) — only the UI shell around them was traced.

## Valence cliffs

1. **Knowledge view flattens the exact thing it exists to un-flatten.** `knowledgeSummary()` hardcodes `statusCounts: {}` and ships the literal string `"Status breakdown pending per-assertion status lookup; see assertion detail"` (`graphForgeSession.ts:906-909`) — and "assertion detail" doesn't help either: `getAssertion()` (`graphForgeSession.ts:942-955`) never calls `assertionStatus()`, so `showAssertion`'s JSON doc has no current-status field, and the Knowledge tree's per-assertion `TreeItem` uses one fixed `"law"` icon regardless of status (`knowledgeTree.ts:52`). There is a working `listAssertionStatus` method on `GraphForgeSession` and a `recordAssertionStatus` write command, but **no read command anywhere in the palette** exposes it. DESIGN.md's stated doctrine is "epistemic status is legible... always named, never flattened to anonymous nodes" — that promise is delivered beautifully in the Ontology and Result Graph surfaces (per the prior audit) but is not delivered at all in the one view whose entire job is epistemic status: the Knowledge ledger itself. This reads less like an oversight in one string and more like a half-shipped feature — FR-11's letter (empty/unavailable/populated states, Show Assertion action) is satisfied, but the feeling contract's spirit for this specific surface is not.
2. **The status-bar tooltip cliff (prior audit, P1) is confirmed worse on the Python side.** `pythonLoader.ts:63-74` builds `python.error` by joining **every candidate interpreter's raw probe failure** — each one itself either a raw subprocess `stderr` string or a raw Python exception (`f'{type(e).__name__}: {e}'`, `pythonProbe.ts:23`) — into one long `"Tried: <path> (<source>): <error> | <path> (<source>): <error> | ..."` string. `describeRuntimeUnavailable()` (`runtimeSelection.ts:66-68`) then interpolates this directly next to the already-known raw Node diagnostic, so a cold machine with neither runtime configured — a completely plausible first install — produces a tooltip that concatenates a raw `require()` stack *and* a joined multi-candidate Python stack trace in the same string. This is the same anti-pattern the prior audit named, but this pass found it's not confined to Node, and the fix needs to cover both `nodePart` and `pythonPart` in the same function, not just the Node half.
3. **`NodeOnlyFeatureError` — a well-worded message, badly delivered.** The message itself is a model example of the product's own doctrine: `` `\`${methodName}\` requires the Node runtime (@graphforge/node). Switch \`graphforge.runtime\` to "node"...` `` (`graphForgeSession.ts:105-113`) — it names the exact fix. But every Power/Checkpoint/Embedding-space command's catch block only special-cases `UnsupportedByBindingError` for the softer `showWarningMessage` treatment (`checkpoints.ts:117-121`, `embeddingSpaces.ts:74-78`, `indexManagement.ts:218-222`, `power.ts:82-86`) — `NodeOnlyFeatureError` falls through to the same red `showErrorMessage` as a genuine failure. For a Python-first analyst (the exact persona FR-14/FR-18 exist to serve), simply trying any Power feature under the runtime they were steered toward reads as an alarming error rather than what it actually is: "this specific advanced feature is Node-only today," a policy fact, not a failure.

## Dead flats

1. **Every Power/Knowledge/Verb command's error path is the same un-curated toast.** Not a single new cliff each — this is the *default*, confirmed across ~25 distinct catch blocks in this pass. The prior audit found this once (Run Query); this pass confirms it's actually the house style, and the existing `recoveryToastMessage` helper (`shared.ts:30-40`) that could fix all of them at once is used nowhere outside its own module.
2. **Analyst verbs don't share Find's best idea.** `find.ts`'s `handleFindError` (lines 100-121) is a genuinely excellent pattern — detect a missing-index signature, offer to run the exact remediation command with the same label pre-filled, right in the error toast's action button. `similar` (which supports `knn`/`cosine`, both index-shaped) and `cluster` (which supports vector-backed algorithms via `vectorProperty`) can plausibly hit the same missing-index condition, but `analystVerbs.ts`'s catch-all (line 264) has no equivalent — it's the generic raw-message toast. The fix exists in the same codebase, one file over; it's just not shared.
3. **The Get Started runtime step's primary CTA can't see what the rest of the product already knows.** `buildGetStartedState` computes a full `environmentSnapshot()` including `projectKind` (`getStartedView.ts:379`), but `runtimeStep.primaryAction` is unconditionally `"Setup Native (Node)"` (`getStartedView.ts:399-401`) — it never checks `projectKind === "python"`. FR-18 explicitly requires the *runtime selection logic* to bias toward Python in Python-first workspaces, and it does (`runtimeSelection.ts:41-43`) — but the *UI that gets a user to that point* doesn't know this exists yet. A brand-new analyst opening a `pyproject.toml` repo with no runtime configured sees "Setup Native (Node)" as the one big button and "Setup Python" tucked into the always-present secondary slot (itself already flagged by the prior audit as dangling/always-shown) — the checklist's loudest suggestion is the wrong runtime for their own workspace.
4. **Power commands read as a coherent internal design doc, not a coherent user-facing tier.** The `#9`/`#10`/`#11` code comments consistently call these "power/engineer commands," "flat, no cascading wizard," "expert-only" — the team clearly has a shared internal concept of "this is a different tier from the analyst-verb palette." None of that concept reaches the palette itself for most of these commands (only the verb `*Advanced` siblings and `showResultGraphAdvanced` get a title marker). A real user browsing the palette can't tell the internal tiering exists.

## Command palette naming consistency (59 entries, mechanical check)

- **Ellipsis inconsistency.** VS Code convention (and this codebase's own majority pattern) is "…" on any command that opens a picker/input chain before executing. `Create Checkpoint…`, `Diff Checkpoints…`, `Attach Evidence…` all follow this. But `Rank`, `Cluster`, `Paths`, `Analyze`, `Similar` (2-3 step QuickPick chains) and `Find` (2-input chain) have **no ellipsis** at all, reading identically to zero-prompt commands like `Refresh Explorer` or `Index Adjacency`. A user can't tell from the palette alone which commands execute immediately and which open a multi-step flow.
- **"(Advanced)" placement is inconsistent.** The verb-Advanced siblings and `showResultGraphAdvanced` use `"X (Advanced)…"` — qualifier before the ellipsis (`Rank (Advanced)…`). `Attach Evidence…`, `Assess Confidence…`, `Record Assertion Status…`, and `Publish Composite Transaction… (Advanced)` use the opposite order — qualifier *after* the ellipsis. Both patterns exist in the same palette for the same semantic purpose ("this is the advanced variant").
- **No palette-visible tier marker for the Power module** (see Dead flat #4) — a real, if minor, gap distinct from the two above since it's not even inconsistent, just absent.
- **What *is* consistent and works well:** the `GraphForge: ` prefix baked into every title (rather than VS Code's separate `category` field) is applied with zero exceptions across all 59 commands — a small, easy-to-get-wrong detail that's actually uniform here. Verb naming (`Rank`/`Cluster`/`Paths`/`Analyze`/`Similar`/`Find`) reads as one deliberate, analyst-facing vocabulary, exactly matching `docs/PRODUCT.md`'s stated verb list. `Open ontology.json` is the one literal-filename title breaking Title Case, but it's a defensible exception (it names an actual file the user will see in their editor tab).

## Python vs Node runtime parity

Positive first: the **uv-only install tone is a model citizen.** `pythonInstallCommand.ts` and `setupPython.ts` never fall back to `pip`, but the messaging never shames a `pip`-habituated user either — "Install uv first" plus a docs link (`setupPython.ts:111-118`) is exactly the "fail closed, name the next step" doctrine done right, and the QuickPick correctly detects `pyproject.toml`/`uv.lock` to offer `uv add` vs `uv pip install` without asking the user to know the difference.

Where parity breaks down:
- **Advanced/Power surfaces are Node-only by architecture, not just by binding gap.** `EngineBackend` (`types.ts:501-552`, the interface `PythonEngineBackend` implements) has no checkpoint, embedding-space, index, capability, descriptor, or composite-transaction methods at all — these aren't "not implemented yet," they're outside the runtime-agnostic contract's scope entirely, confirmed by `NodeOnlyFeatureError`'s existence as a dedicated class. A Python-first analyst (the persona FR-14/FR-18 were built for) who successfully sets up Python per the onboarding checklist will find the entire second half of the command palette — checkpoints, embedding spaces, indexing, power — gated behind a runtime they were never told is required for those specific features until they try one and hit cliff #3 above.
- **The onboarding UI doesn't yet reflect the Python-first bias the runtime-selection logic already has** (Dead flat #3) — this is the most actionable, most surprising finding in this section, because the underlying logic (`chooseRuntime`, `detectWorkspaceProjectKind`) already does the right thing; only the checklist's static `primaryAction` assignment hasn't caught up.
- **Diagnostic verbosity is symmetric in the wrong way** — cliff #2 shows the Python side's raw-error path is not just "as bad as" the known Node cliff, it's structurally worse (multi-candidate join vs single message).

## Agent persona / interop contract — does it hold everywhere?

**No.** This is the single largest finding of this pass. `docs/experience/agent-interop.md`'s command table documents exactly 17 command IDs (`checkEnvironment`, `setupNativeBinding`, `setupPythonBinding`, `initializeProjectHere`, `openProject`, `runQuery`, `runQueryWithParams`, the 5 verbs + their `*Advanced` variants, `find`, `showOntology`, `showResultGraph`, `showResultGraphAdvanced`, `showCapabilities`, `loadOntology`, `refreshExplorer`) as "the agent-facing contract." The package contributes **59** commands. The other ~30 — all 6 checkpoint commands, all 6 embedding-space commands, all 6 index-management commands, all 5 power commands, and all 7 knowledge commands — are:

1. **Not mentioned in `agent-interop.md` at all**, positive or negative (contrast with the verb commands, which *are* documented as a known, tracked gap under issue #4 in the same doc's "Gaps / follow-ups" section — the doc is honest about verb args, but silent about this entire other half).
2. **Registered with `void`-returning handlers.** Every one of these 30 commands is wired as `vscode.commands.registerCommand("graphforge.X", async () => { await runX(session); })` — the handler's return value is discarded, so `executeCommand("graphforge.X")` always resolves to `undefined`, success or failure. Confirmed directly in `checkpoints.ts`, `embeddingSpaces.ts`, `indexManagement.ts`, `power.ts`, and `knowledgeCommands.ts` — none return the JSON payload they compute and write into the opened editor document.
3. **Excluded even from the CI "safe commands" smoke suite** (`src/test/extension.test.ts:112-204`) that proves the documented contract for the other 17 — they only appear in the plain registration-exists list, with no execution or shape assertion at all, and are absent from the file's own "NOT executed here" explanation comment too (that comment only accounts for verbs, setup, init, and ontology-loading — it doesn't mention checkpoints/embeddings/index/power/knowledge by name, because the test author's mental model of "the command surface" evidently didn't include them either).

**Why this matters more than a typical documentation gap:** `agent-interop.md`'s own stated purpose is proving, in CI, that a coding agent can drive GraphForge without a human clicking through the palette. An agent (or a person directing one) who reads that doc as the ground truth for "what's automatable" would reasonably conclude the other 30 commands don't exist or aren't meant to be called this way — when in fact they're perfectly callable, they just silently hand back nothing useful. This is a **fail-open**, not a fail-closed, gap: the doctrine "never a bare exception, always name what to do next" (the doc's own "Fail closed" constraint) holds for the 17 documented commands and is simply unaddressed for the other 30, which is a different, quieter failure mode than the raw-error-toast cliffs above — it's not that the JSON is bad, it's that for an agent caller there's no JSON at all.

## Accessibility floor

- All newly-audited surfaces (Knowledge tree, checkpoints, embedding spaces, indexing, power) use native VS Code `TreeItem`/`showQuickPick`/`showInputBox`/`showWarningMessage` primitives exclusively — no custom-drawn controls. This inherits VS Code's own keyboard/screen-reader/high-contrast support by construction, in contrast to the prior audit's P0 finding about the Get Started Welcome cards' custom `.radio` div. **No new P0 accessibility candidate found in this pass** — worth stating explicitly per audit method step 7, since the prior audit's P0 was scoped to one specific control, not the whole product.
- The severity-scaled confirmation pattern (single modal for Delete, modal + retype for Revert, three-way choice for Composite Transaction) is itself a quiet accessibility/cognitive-load win: it doesn't ask for the same amount of friction regardless of stakes, which is friendlier to a screen-reader or keyboard-only user who has to traverse every dialog step manually — fewer, better-calibrated steps for lower-risk actions.

## P0 / P1 / P2

**P0 — none newly found in this pass.** (The prior audit's Welcome-card ARIA P0 stands; this pass found no new accessibility blocker.)

**P1 — trust dilution and contract gaps**
- Make the Knowledge tree/summary/detail actually show epistemic status per assertion — wire a real status lookup into `knowledgeSummary()`/`getAssertion()` (the `listAssertionStatus` session method already exists) and stop hardcoding `statusCounts: {}`; add a palette command to read status, mirroring the existing write-only `recordAssertionStatus`. *New issue candidate — the single highest-priority finding in this pass, since it's a direct contradiction of the stated feeling contract in the surface built specifically for it.*
- Extend `describeRuntimeUnavailable()`'s curation (not just the Node half) to stop joining raw multi-candidate Python stderr/exception text into the status-bar tooltip. *New issue candidate, but frame as "finish the P1 already filed against this function for Node" — same fix, now proven to need both branches.*
- Route the ~25 raw `showErrorMessage(`X: ${errorMessage(err)}`)` catch blocks across checkpoints/embedding-spaces/index-management/power/knowledge/verb commands through the existing (still-unused) `recoveryToastMessage` helper or an equivalent. *New issue candidate — same root cause as the already-filed Run Query one, but this pass found it's the default pattern across ~25 call sites, not an isolated case; likely worth one shared fix (e.g., a `reportEngineError` helper alongside the existing `reportCheckpointError`/`reportError` near-duplicates) rather than 25 individual patches.*
- Document (or implement) an agent-facing contract for the ~30 commands `agent-interop.md` doesn't cover — at minimum, return the JSON each handler already computes from `executeCommand` instead of discarding it, and add them to the doc's table (even if just to state "human-only today, no args-based bypass yet" the way the verb gap is documented). *New issue candidate — largest scope finding in this pass.*
- Have the Get Started checklist's runtime-step primary CTA respect the already-computed `projectKind` (default to "Setup Python" when `projectKind === "python"`, mirroring `chooseRuntime`'s own logic) instead of hardcoding "Setup Native (Node)". *New issue candidate, small, high-leverage — the underlying logic already exists.*
- Have Power/Checkpoint/Embedding commands' catch blocks special-case `NodeOnlyFeatureError` with the same `showWarningMessage` (not error) treatment already given to `UnsupportedByBindingError` — a Python-runtime user hitting a Node-only feature is a policy/config fact, not a failure. *New issue candidate, small.*

**P2 — polish and voice**
- Give `similar`/`cluster`'s catch blocks the same missing-index remediation pattern `find.ts` already has (offer to run Index Text/Index Vector inline). *New issue candidate.*
- Add one-line `detail` text to the raw-enum QuickPicks (`WRITE_MODES`, `DIFF_SCOPES`/`DIFF_DETAILS`, `GRAPH_KINDS`, `SOURCE_KINDS`, `EVIDENCE_ROLES`, `CONFIDENCE_POLICIES`) so analysts see plain-language glosses instead of bare engine tokens. *New issue candidate.*
- Reword `runEnableCapability`'s confirmation ("atomically mutates the project's capability manifest") to match the product's own Voice doctrine — plain-language equivalent, e.g. "This changes what your project can do and can't be undone here." *New issue candidate, small.*
- Reconcile the two "(Advanced)" placement conventions (`"X (Advanced)…"` vs `"X… (Advanced)"`) to one order across the palette. *New issue candidate, small.*
- Consider a lightweight palette-visible signal (consistent "(Advanced)" suffix, or a shared word) for the Power module's non-`*Advanced`-suffixed commands (`Enable Capability…`, `Export Invocation Descriptor…`, `Open with Write Mode…`, `List Algorithm Runs`, and arguably the checkpoint/embedding-space commands), so the analyst/integrator tiering the code already has internally is visible externally too. *New issue candidate.*
- Suggest running `Diff Checkpoints…` before `Revert to Checkpoint…` in the revert flow's own copy — the safest possible revert already exists one command away and isn't mentioned. *New issue candidate, small.*
