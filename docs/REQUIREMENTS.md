# Requirements

Contract for the GraphForge VS Code extension: editor workbench over the embedded
engine so analysts can run Cypher and analyst verbs, browse ontology and knowledge
context, and view epistemic-aware result graphs.

## Functional requirements

| ID | Requirement | Derived from | Acceptance behavior |
|---|---|---|---|
| FR-1 | The system shall register language id `cypher` for `.cypher` and `.cql` with TextMate highlighting. | PRODUCT — Cypher first-class | Given a `.cypher` file, When opened, Then language mode is Cypher and keywords highlight. |
| FR-2 | The system shall provide **Run Query** using editor selection or document text via `forge.execute`, persist the canonical `{ columns, rows, rowCount }` JSON result under the open project, and show it in an interactive table in the bottom Panel area. | PRODUCT — Cypher | Given an open project, When Run Query succeeds, Then `results/query-result.json` and `results/query-result.md` are written inside that project; the Results panel reveals a table with expandable nested/mixed values, and optionally a result graph opens. |
| FR-3 | The system shall expose analyst verb commands: Rank, Cluster, Paths, Analyze, Similar, Find. | PRODUCT — verbs first-class | Given an open project, When a verb command runs with QuickPick inputs, Then the engine is invoked and results are shown. |
| FR-4 | The system shall detect GraphForge projects only when `FORMAT` equals `graphforge-project/v1\n`. | Engine project format | Given a folder with exact FORMAT bytes, When the explorer refreshes, Then the project appears; wrong FORMAT does not. |
| FR-5 | The system shall provide Activity Bar views: Projects, Ontology, Knowledge. These supporting views shall start collapsed when the GraphForge container first opens, leaving Get Started as the primary surface; users may expand them normally. | PRODUCT — workbench | Given activation, When the GraphForge container first opens, Then all three supporting views are present and collapsed. When a user expands a view, Then ordinary VS Code view-state behavior applies. |
| FR-6 | The system shall open an Ontology Viewer webview showing mode and entity/relation/property trees. | PRODUCT — ontology | Given a project, When Show Ontology runs, Then mode badge and types render (or empty exploratory state). |
| FR-7 | The system shall open a Vite-built Result Graph over the stable `GraphPayload`. New saved graphs default to Cytoscape Canvas with a fully materialized CoSE configuration; AntV G6 Canvas and Sigma WebGL remain explicit alternatives. The selected renderer, backend, layout, style, interactions, filters, and optional Timebar bindings belong to the visualization artifact. A saved choice is not overridden by later setting changes and a renderer/layout failure never silently substitutes another. While a renderer is not yet usable, the provisional canvas remains covered by a renderer-specific, accessible pipeline status naming the current truthful phase without invented percentages. | PRODUCT — epistemic viz; Issues #65/#67 | Given a new graph visualization, When it is saved, Then its complete Cytoscape configuration exists in a v2 artifact before open. Given a v1 or v2 saved graph, When it opens, Then its recorded renderer is used and the file is not rewritten. Given G6, Cytoscape, Sigma, G2, L7, or Plotly is rendering, Then the panel names its data/layout-or-composition/paint phase and exposes the canvas only after readiness. Given renderer failure, Then a structured failure is shown and no fallback runs. |
| FR-8 | The system shall fail closed with a clear message when `@curatelabs/graphforge` cannot be loaded. | PRODUCT — quality | Given no native binding, When Open Project / Run Query is attempted, Then an error explains linking the binding. |
| FR-9 | The system shall provide **Create Assertion…** with minimal fields (claim, subject UUID, subject kind) via the palette, minting UUIDv7 identities client-side. | PRODUCT — Knowledge (#6) | Given an open project, When Create Assertion runs and the claim/subject are provided, Then one assertion is written and the Knowledge view refreshes to show it. |
| FR-10 | The system shall provide separate Advanced commands — **Attach Evidence…**, **Assess Confidence…**, **Record Assertion Status…** — kept out of Create Assertion. | PRODUCT — Knowledge (#6) | Given an existing assertion, When an Advanced command runs, Then the corresponding immutable ledger write completes without needing to know it exists during Create Assertion. |
| FR-11 | The Knowledge view shall render list/empty/inspect states: no project, capability unavailable, empty ledger, and a populated assertion list with a **Show Assertion** action per item. | PRODUCT — Knowledge (#6) | Given each state, When the view refreshes, Then it shows a matching, actionable node (not a blank tree). |
| FR-12 | The Ontology view and viewer shall render a helpful empty state in exploratory mode (not an error) with an obvious **Load Ontology…** action, and refresh both immediately after a load. | PRODUCT — Ontology (#7) | Given exploratory mode with no ontology loaded, When the view/viewer render, Then they explain the mode and offer Load Ontology…; after loading, both refresh to the new ontology. |
| FR-13 | The Ontology viewer shall expose an **Advanced** section to open the raw `ontology.json` and explain the current progressive mode (exploratory/advisory/strict). | PRODUCT — Ontology (#7) | Given the viewer is open, When Advanced → Open ontology.json / Explain Ontology Mode runs, Then the file or an explanation document opens. |
| FR-14 | The system shall support a Python `graphforge` runtime as a first-class alternative to `@curatelabs/graphforge`, selected via `graphforge.runtime` (default `auto`). In `auto`, Node is the global default **except** when the workspace looks Python-first (see FR-18), in which case Python is preferred when usable. | Issue #12 | Given `graphforge.runtime` is `python`, or `auto` with Node unavailable, or `auto` in a Python-first workspace with Python usable, When a project is opened, Then Cypher execute and at least one analyst verb (rank) run through the Python bridge with the same result shape as the Node path. |
| FR-15 | The system shall provide `GraphForge: Check Environment` reporting both Node-binding and Python-interpreter/`graphforge`-import status, which runtime is active, the detected project kind, and one next action. | Issue #12 (extends #2) | Given the command runs, When the report is shown, Then it is agent-copyable JSON plus a 3-line human summary covering runtime, project, and next step. |
| FR-16 | The system shall provide `GraphForge: Setup Python Binding` as a single QuickPick (≤3 choices: use detected interpreter, select interpreter, install `graphforge` via **uv** with explicit consent). Package installs use **uv only, never pip**; if `uv` is not installed, the command tells the user to install uv first instead of falling back to pip. | Issue #12 (UX doctrine from #1: palette-first, no cascading menus; uv-only per product feedback) | Given the command runs, When a choice is made, Then `graphforge.pythonInterpreterPath` is set and/or `uv add graphforge` (in a uv project) or `uv pip install graphforge` runs only after an explicit confirmation dialog; if `uv` is missing, no install command runs and the user is directed to install uv. |
| FR-17 | The system shall detect Python interpreters in priority order: explicit config, VS Code Python extension selection, workspace venv (`.venv`/`venv`/`env`/`.conda`), then PATH. | Issue #12 | Given multiple candidates exist, When resolving, Then the first one with an importable `graphforge` wins. |
| FR-18 | The system shall classify the workspace as Python-first, Node-ish, or ambiguous based on Python markers (`pyproject.toml`, `requirements.txt`, `uv.lock`, `.python-version`, `Pipfile`, `environment.yml`, `setup.py`, notebook-dominant root, or an explicitly selected VS Code Python interpreter) versus Node markers (`package.json`), and use this to bias `graphforge.runtime: auto` toward Python in Python-first workspaces even when `@curatelabs/graphforge` is available. When both marker sets are present, Python wins only given a strong signal (`pyproject.toml`/`uv.lock`, or Python `graphforge` already usable); otherwise the workspace is ambiguous and Node stays the default. | Issue #12 (product feedback: Python-prefer in Python repos) | Given a workspace with `pyproject.toml` and no `package.json`, When `graphforge.runtime` is `auto` and both Node and Python are usable, Then Python is selected. Given a workspace with both `package.json` and `pyproject.toml`/`uv.lock`, When `auto` resolves, Then Python is still selected. An explicit `graphforge.runtime` of `node` or `python` always overrides project-kind detection. |
| FR-19 | The system shall make Plotly the creation default for saved analytical chart artifacts while retaining AntV G2 as an explicit chart option and the required temporal adapter. The **Figure** webview handles raw Plotly figure JSON plus v1 and v2 Plotly charts. Optional Plotly size limits default off. All renderer assets are bundled locally; failures return structured errors without replacing a prior valid artifact or panel state. | Issues #62/#67 | Given explicit chart bindings with no renderer override, When a chart artifact is created, Then a complete Plotly v2 spec is saved and returned. Given an explicit G2 renderer, Then a complete G2 v2 spec is saved. Given raw Plotly JSON or an existing Plotly artifact, When opened, Then the retained Figure adapter runs without migration. |
| FR-20 | The system shall provide a **quickstart sample** (`graphforge.openSampleProject`) built from the vendored Apache-2.0 US air-routes dataset. Its query, Python/Jupyter notebook, Streamlit app, source data, seed mutation, supporting temporal result, and v1/v2 graph/chart/geospatial/temporal specs shall be project files copied into the sample. Without an explicit path, the command shall create the project at `~/Downloads/graphforge-quickstart`, never in the IDE workspace or extension-private storage. The Python notebook and Streamlit app shall use GraphForge Python directly for native graph analytics and provide Python-native output, never requiring VS Code result or visualization artifacts. | Issue #63 + #67 | Given a usable runtime, When Try sample runs without a path, Then a FORMAT project opens at `~/Downloads/graphforge-quickstart` with visible `queries/`, `notebooks/`, `apps/`, `results/`, `visualizations/`, `data/`, and `mutations/`. Given an explicit path, When the command runs, Then it uses that path. Given a Python kernel with GraphForge, pandas, PyArrow, and Plotly, When the notebook runs top to bottom, Then it reads the copied 586-airport/7,430-route CSVs, runs native PageRank, renders Plotly, and writes a portable CSV plus self-contained HTML under `notebooks/outputs/`. Given `streamlit`, When the app is run with its documented `uv run` command, Then it renders the same Python-native PageRank dashboard in a browser. |
| FR-21 | The Results panel shall link table selections to an open Result Graph using explicit node/edge IDs, identity-like values (including codes), or graph-shaped row endpoints; graph selections shall reveal matching result rows. | PRODUCT — linked exploration | Given a result row containing `source`/`target` or an identity cell, When the user selects it, Then matching graph elements highlight. Given a graph node/edge click, Then matching table rows highlight. Figure linking is excluded until figure traces retain source-row provenance. |
| FR-22 | Get Started shall show one persistent **Environment → Project → Query → Result → Visualize** journey tree, with exactly one current node and its simplest primary next action. Progress shall come from runtime state and user-visible project artifacts, not a startup persona, hidden completion flag, or automatic project selection. The sample Query node shall also expose its project-owned Python notebook and Streamlit app as parallel analyst paths. **Hub / Query / Visualize** remain available; Query lists every durable result including `results/query-result.json`, while Visualize lists, creates, filters, saves, and reopens graph, chart, geospatial, and temporal artifacts from explicit result-column choices. An artifact whose source result does not exist is visibly unavailable rather than exposed as a dead Open action. `graphforge.resultGraph.renderer` and `graphforge.chart.renderer` are creation templates, not live overrides for saved work. | Product feedback + #67 | Given the sample project, When Query is current or complete, Then **Open Python notebook** opens `notebooks/air-routes-analysis.ipynb` and **Open Streamlit app** opens `apps/air_routes_dashboard.py`, each without installing packages or selecting a kernel. Given any startup state, Then all five nodes remain visible and one available incomplete node is current. Given Visualize creates a view, Then a complete v2 artifact is saved before its renderer opens. |
| FR-23 | Durable workbench state shall live inside the open project using `queries/`, `results/`, `visualizations/`, and `mutations/` (or `data/`). Material visualization changes shall show dirty state and require explicit Save; Revert restores the last committed artifact. Hover, transient selection, and the current playback frame may remain session-only. | Product mandate + #67 | Given a viewport or temporal range change, When it occurs, Then Save/Revert become available. Given Save, Then the validated spec is replaced; Given Revert, Then the committed spec is restored. |
| FR-24 | IDE coding agents shall have versioned context plus stable path-driven artifact operations. `graphforge.createProjectVisualization` requires explicit bindings and `create`/`save` return `{ path, spec, panel? }`; open returns the saved spec and panel outcome. Mutations remain separately confirmed. | Agent interoperability tuning + #67 | Given an agent creates a visualization with complete arguments, When the command resolves, Then the returned path identifies a saved project artifact and the returned spec contains every material renderer decision without webview scraping. |
| FR-25 | Query, Visualize, Import, and Integration (shown as Connect) shall use one manifest-driven module manager for discovery, installation, enablement, activation, deactivation, and status. Query, Visualize, and Import are default modules: they ship installed and enabled, may be disabled, and cannot be removed through the module lifecycle. | PRODUCT — modular workbench | Given first activation, When module state is initialized, Then all three default modules are installed, enabled, and marked non-removable. When a module is disabled, its registrations are disposed without reloading the extension host. |
| FR-26 | The module manager shall discover modules from three provider kinds: default manifests, the optional GraphForge `moduleCatalog()` binding surface, and side-loaded manifests. The future GraphForge catalog is the normal distribution path for modules not shipped in this repository; side-loading is an advanced/local path. All providers shall be validated by the same manifest contract. | Module architecture | Given catalog or side-loaded providers return valid manifests, When discovery refreshes, Then every module appears in one inventory with its source and status. Given an older binding without `moduleCatalog()`, Then discovery continues with an empty GraphForge catalog. Given an invalid or reserved side-loaded manifest, Then installation fails without executing module code. |
| FR-27 | `GraphForge: Manage Modules` shall open a Vite-built Module Bay that filters by capability and shows source, version, status, install, enable/disable, remove, and available module actions. The extension host shall remain authoritative for every state transition. | DESIGN — Module Bay | Given modules from multiple providers, When the Module Bay opens or an action completes, Then it renders the latest host snapshot in VS Code themes with keyboard-accessible controls; first-party modules do not offer Remove. |
| FR-28 | The first-party Import module shall import CSV, JSON, JSONL, and NDJSON files as nodes through a parameterized engine mutation. It shall support create or merge mode, an analyst-selected label and identifier property, explicit confirmation, a 25 MB file limit, and a 100,000-row limit. | PRODUCT — Import module | Given a supported local file and confirmed options, When Import Data runs, Then rows are parsed and written using parameters and a structured result reports the imported count. Given invalid data, a missing merge identifier, cancellation, or a size/row limit violation, Then no mutation is submitted and the failure is actionable. |
| FR-29 | The system shall render v2 geospatial artifacts with L7 and v2 temporal artifacts with G2 from explicit bindings. Geospatial specs record point coordinates, source/target link coordinates, or GeoJSON; CRS, projection, ordered point/arc/line/polygon layers, an explicit blank offline basemap, and viewport. Link artifacts render saved arc layers between their endpoint nodes without inferred field names. Temporal specs record timestamp, timezone, granularity, value/series, range, window, and playback. Both expose an accessible filtered-data companion. | Issue #67 | Given explicit source and target longitude/latitude bindings plus an arc layer, When the artifact opens offline, Then L7 draws curved links between the deduplicated endpoint points. Given complete geo or temporal bindings, When the artifact opens offline, Then its saved settings drive the view and companion table. Given an incomplete or remote-data configuration, Then validation fails without inference or network fallback. |

## Non-functional requirements

| ID | Quality attribute | Target / constraint | Why it matters |
|---|---|---|---|
| NFR-1 | Compatibility | VS Code `^1.96`, Node `>=20` | Aligns with engine Node bindings. |
| NFR-2 | Correctness boundary | No reimplementation of Cypher/verb/epistemic semantics in the extension (Node **or** Python path) | Engine is source of truth. |
| NFR-3 | Portability | Native addon resolved via optional peer, config path, or sibling monorepo | Dev and CI can work without published npm binary. |
| NFR-4 | License | Apache-2.0, publisher CurateLabsAI | Matches GraphForge engine. |
| NFR-5 | Default runtime | `@curatelabs/graphforge` remains the global default for Node-ish and ambiguous workspaces; Python is preferred in `auto` only for Python-first workspaces (or as a fallback when Node is unavailable), and an explicit `graphforge.runtime` setting always overrides project-kind detection | Issue #12 constraint from product. |
| NFR-6 | Fail-closed dual runtime | When neither runtime is usable, error messages and recovery actions must cover both setup paths | Issue #12 — no dead-end failures. |
| NFR-7 | Python packaging | Python setup/install flows use `uv` exclusively (`uv add` / `uv pip install`); the extension never shells out to `pip` and does not fall back to it when `uv` is missing | Ship policy — uv only, never pip. |
| NFR-8 | Module safety | Side-loaded modules are declarative by default. A `workspace-script` entrypoint is allowed only when the machine-scoped `graphforge.modules.dangerouslyAllowWorkspaceJavaScript` user setting is explicitly enabled, VS Code trusts the workspace, the resolved `.js`/`.cjs` file remains inside the module folder, and the user accepts a per-install modal warning. Turning the setting off deactivates and disables installed workspace-script modules. Reserved GraphForge identifiers cannot be claimed by side-loaded providers. | A repository cannot grant itself extension-host code execution through workspace settings or path traversal. |
| NFR-9 | Module isolation | Every activation receives a scoped disposable store, and disabling or removing a module disposes only that module's registrations. | Modules must be independently controllable without leaking commands, listeners, or panels. |
| NFR-10 | Visualization safety | v2 specs are validated JSON only; no callbacks, `eval`, CDN, remote data fetch, implicit map provider, embedded credential, or broadened CSP. | A project artifact must not become code execution or covert network authority. |
| NFR-11 | Visualization compatibility | v1 Cytoscape/Sigma/Plotly specs remain readable and are never rewritten merely by opening them; v2 is the writer default. | Existing project artifacts remain reproducible. |
| NFR-12 | Performance evidence | Comparative stress work is opt-in and one-off, never a required PR/push/scheduled/release gate or an automatic renderer threshold. | Vendor or Node-preparation measurements do not prove browser rendering behavior. |

| Requirement | Given | When | Then |
|---|---|---|---|
| FR-4 | Folder with exact FORMAT marker | Discover projects | Project listed under Projects view |
| FR-2 / FR-21 | Open project + Cypher buffer | Run Query, then select a table row | Project-local result documents + bottom Results panel; an open Result Graph highlights matching entities |

## Constraints & assumptions

- **Constraint:** Visualization colors for epistemic status are extension-owned (no product palette yet).
- **Constraint:** Committed ontology lives under `generations/<uuid>/participants/workspace/ontology.json`.
- **Assumption:** `@curatelabs/graphforge` returns Arrow IPC buffers decodable by `apache-arrow`, synchronously or as a Promise (knowledge-ledger writes are async `AsyncTask`s on the Node side as of this writing).
- **Assumption:** Identity UUIDs for assertions/evidence/confidence/status events must be UUIDv7 (engine-enforced); the extension mints them client-side via `session/uuid.ts`. Operation/idempotency UUIDs accept any version.
- **Constraint:** `recordAssertionStatus` requires an existing `provenanceUuid`; until there is a provenance picker, the analyst pastes one in directly (Advanced command).
- **Assumption:** Every knowledge-ledger native method is optional on `GraphForgeNative` and feature-detected at call time — the sibling engine API is still moving.
- **Constraint:** A module's provider describes where it came from; capability
  (`query`, `visualize`, `import`, `integration`) describes what it adds. Neither is
  inferred from its installation method.
- **Assumption:** `GraphForgeNative.moduleCatalog()` is optional and may be absent
  or return no entries until engine-owned modules are registered by the GraphForge
  project.

## Dependencies

- `@curatelabs/graphforge` — native engine facade (default runtime)
- `graphforge` (PyPI) + `pyarrow` — Python engine facade (alternative runtime, #12); resolved in
  a user-selected interpreter, never bundled with the extension
- `apache-arrow` — IPC table decode (shared by both runtimes)
- `cytoscape` — default Result Graph Canvas renderer and CoSE force layout
- `@antv/g6` + `@antv/layout` — explicit Result Graph Canvas renderer and worker ForceAtlas2 layout
- `@antv/g2` — explicit analytical chart renderer and required temporal renderer
- `@antv/l7` + `@antv/l7-maps` — first-class geospatial renderer with an explicit blank offline map
- `sigma` + `graphology` + `graphology-layout-forceatlas2` — retained WebGL Result Graph adapter and force layout
- `plotly.js` — default analytical chart renderer plus raw Figure and v1 compatibility paths
- GraphForge engine project format and ontology participant layout
- Optional GraphForge engine module catalog (`moduleCatalog()`); absence is a
  supported compatibility state
